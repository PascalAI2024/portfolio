# Public Portfolio — Design Direction

## Overview

This is a documentation-first public GitHub portfolio for selected PascalAI and
Ingenious Digital work. It is for prospective clients, collaborators, and
technical reviewers who need to understand the range of work and the quality of
judgment without receiving private code, client information, infrastructure
topology, or reusable internal operating methods.

**Feel:** precise, evidence-led, quietly ambitious.

**Must not feel:** a generic agency landing page, a badge wall, a code dump, or
a dark theme used as camouflage for vague claims.

## Visual Direction

The chosen direction is **Dark Signal Room**: deep midnight surfaces, restrained
cyan and amber signals, compact evidence panels, and simple high-level system
maps. This is a visual language for repository diagrams and cleared assets, not
a separate website.

## Colors

- Midnight `#08111F` — diagram field and dark asset background.
- Signal cyan `#47D7FF` — verified flows and active evidence.
- Evidence amber `#F2B84B` — decisions, constraints, and caveats.
- Mist `#D9E5F5` — primary text on dark assets.
- Slate `#6F829C` — secondary labels and connector lines.

All published diagrams must retain clear contrast in GitHub light and dark
rendering, including a text-only Markdown equivalent where needed.

## Typography

GitHub provides the reading surface. Use its native Markdown typography for
prose. Generated visual assets use a high-contrast geometric sans for labels
and a restrained mono face for evidence metadata. Never make reading depend on
an image.

## Section Grammar

1. A concise thesis and public boundary.
2. A visual capability map, grouped by problem domain.
3. Four to six flagship case studies.
4. A wider, linked project catalogue.
5. Public proof, methods, and disclosures.

Every case study follows: **brief → decisive move → system shape → evidence →
boundary**. Diagrams show context and decision flow, never private topology or
operational recipes.

## Motion System

None. GitHub Markdown is the primary medium. Static SVG and Mermaid diagrams
must communicate clearly without animation.

## Components

- **Capability map:** compact table plus icon-free diagram; each lane links to
  proof rather than a technology inventory.
- **Case-study card:** one-sentence outcome, role, relevant domains, and a
  public-safe disclosure label.
- **System shape:** a redacted Mermaid or SVG context diagram with a prose
  summary.
- **Boundary note:** explicit statement of what is intentionally omitted.

## Elevation & Depth

Use rules, negative space, and small signal accents. No fake dashboards,
gradients, glass panels, or decorative device frames.

## Shapes

Rectangular diagrams with modest rounding only where it communicates a system
boundary. Avoid pills, badges, and ornamental cards.

## Responsive Behavior

README and case studies must work as linear Markdown first. Wide diagrams need
a concise text alternative and should remain readable in GitHub mobile view.

## Do's and Don'ts

- Do show the problem, decision, proof, and professional judgment.
- Do distinguish public proof from private architecture stories.
- Do make each technology mention earn its place through a project or outcome.
- Do not publish credentials, client data, private source, live access paths,
  deployment instructions, security controls, or unverified outcomes.
- Do not list every repository as though all are equal.

## Anti-Defaults

Reject generic technology-logo grids, fabricated metrics, portfolio tiles with
no context, and diagrams that look impressive but reveal nothing true.
