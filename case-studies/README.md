# Case Studies

This folder holds the public record of selected work. A case study is a finished, publishable narrative — not an activity log and not an internal postmortem.

## Format

Use this compact structure:

1. **The brief** — the user, business, or product problem in public-safe language.
2. **The move** — the key product or technical decision.
3. **The build** — diagrams, screens, interaction clips, or short excerpts that prove the craft.
4. **The evidence** — measured result, validation method, or what was learned.
5. **The boundary** — what is deliberately omitted and why.

## Editorial rules

- Lead with the work, not the tool list.
- Prefer annotated visuals and small decisive metrics over long prose.
- Name a client only with explicit permission; otherwise describe the work by sector and problem.
- Use redacted, synthetic, or recreated examples when the real artifact is private.
- Keep implementation detail high-level enough to be useful, but not reusable as an access path or a private operating manual.

## Pipeline

`candidate` → `clearance` → `draft` → `visual proof` → `review` → `published`

Nothing moves to `published` until the public-safe review is complete.
